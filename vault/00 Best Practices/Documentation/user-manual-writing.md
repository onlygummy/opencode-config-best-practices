# Writing Web Application User Manuals

## Summary

คู่มือการเขียน user manual สำหรับเว็บแอปพลิเคชัน ตามมาตรฐาน Google/Microsoft/TechSmith — เน้น task-focused, procedure rules, screenshots guidelines

## Problem

คู่มือผู้ใช้缺乏 standard ทำให้คุณภาพไม่สม่ำเสมอ, เขียนแบบบรรยาย UI แทนที่จะโฟกัสงานของผู้ใช้, และไม่มี guidelines สำหรับ screenshots และ annotations

## When to Use

- เขียนหรือปรับปรุงคู่มือผู้ใช้ (user manual) สำหรับเว็บแอปพลิเคชัน
- Review คู่มือที่มีอยู่เทียบมาตรฐาน
- จัดทำ Quick Start, glossary, หรือแนวทางแคปรูป

## Solution

### 1. Task-Focused (โฟกัสงาน ไม่ใช่ widget)

- เขียนเป็นเป้าหมายของผู้ใช้: "เพื่อ X ให้ทำ Y" แทนการบรรยายส่วนประกอบ UI
- รู้จักผู้ใช้: เขียนเพื่อผู้ใช้ ไม่ใช่นักพัฒนา ตัดศัพท์เทคนิคและอักษรย่อที่ไม่จำเป็น

### 2. Procedure Rules (Google: Procedures)

| กฎ | ตัวอย่าง |
|----|----------|
| 1 การกระทำต่อ 1 ขั้นตอน | แยก "กรอก X" กับ "กด Enter" |
| ขึ้นต้นขั้นตอนด้วยคำกริยาสั่ง | "กรอกชื่อ..." ไม่ใช่ "คุณจะต้อง..." |
| เป้าหมายมาก่อนการกระทำ | "เพื่อสร้างรายงาน กด **อัปโหลด Plant Load**" |
| บอกตำแหน่งก่อนการกระทำ | "ในช่อง **ชื่อ** กรอก..." ไม่ใช่ "กรอก... ในช่อง **ชื่อ**" |
| ผลลัพธ์ต่อท้ายขั้นตอน | "กด **บันทึก** ระบบกลับไปหน้ารายการ" |
| งานซ้ำ → อ้างข้ามบท ไม่เขียนซ้ำ | "ดูได้จากบทที่ 3" |
| ห้าม "please" ห้าม "above/below" | ใช้ "ตามภาพที่ X.Y" แทน "ภาพด้านบน" |
| ขั้นตอนทางเลือกขึ้นต้น "Optional:" | "Optional: ..." |

- **ห้ามคำบอกทิศทาง** (บน/ล่าง/ขวา) เป็นหลัก — ใช้ชื่อปุ่ม + ไอคอน หรือใส่รูปแทน

### 3. UI Element Naming (Google: UI elements)

- **Bold ชื่อ label** (`**บันทึก**`) ไม่ใช้ code font กับ UI element, ไม่ใส่เครื่องหมายคำพูด
- ใช้ชื่อตาม label จริง ไม่ใช่ "ปุ่มรูปถังขยะ" → "ปุ่ม **ลบ** (ไอคอนถังขยะ)"
- ปุ่ม icon-only → ใช้ชื่อจาก tooltip + ไอคอน
- checkbox: ใช้ "เลือก/ยกเลิกการเลือก" แทน check/uncheck (กำกวม)
- Tab: "แท็บ **MANDEC**"

### 4. Screenshots (Google Images + TechSmith)

- **Crop เฉพาะส่วนที่เกี่ยวข้อง** (โชว์แค่ปุ่มเดียวก็ตัดให้เห็นแค่ปุ่ม)
- **Annotate เสมอ** (วงกลม/ลูกศร/ตัวเลข) — TechSmith study: ผู้ใช้ทำงานสำเร็จดีขึ้น 67% เมื่อใช้รูปที่ annotate
- **ห้าม PII**: ถ้าติดข้อมูลส่วนบุคคล ใช้กล่องสีทึบปิด 100% (ห้าม blur — กู้คืนได้)
- ความสม่ำเสมอ: ใช้ OS/เบราว์เซอร์/ขนาดหน้าต่างเดียวกันทั้งเล่ม
- Caption = ประโยคสมบูรณ์; อ้างอิงรูปด้วยหมายเลข ("ตามภาพที่ X.Y") ไม่ใช่ "ภาพด้านบน"
- แคปด้วยข้อมูลตัวอย่าง (กรอกข้อมูลเสมือนไว้) เข้าใจง่ายกว่าหน้าจอว่าง
- ชื่อไฟล์สื่อความหมาย

### 5. Structure (TechSmith)

- ต้องมี **สารบัญ** — ผู้ใช้อ่านแบบเปิดหาหัวข้อ ไม่ได้อ่านรวดเดียวจบ
- มี **Quick Start / เริ่มใช้ด่วน** สั้น ๆ ตอนต้น
- **อธิบายสัญลักษณ์/ไอคอน/คำศัพท์ตั้งแต่ต้น** (glossary) — อย่าปล่อยให้เดา
- เรียงพื้นฐาน → ขั้นสูง ตาม logical flow
- มีส่วน **ข้อควรระวัง** ท้ายบท
- ใช้ template เดียวกันทุกบท

### 6. Process

- **ทดสอบกับผู้ใช้ที่ไม่เคยใช้ระบบ** (naive users) ให้ลองทำตามคู่มือ แล้วแก้จุดที่ติด
- Plain language: เขียนเพื่อผู้ใช้ ไม่ใช่นักพัฒนา

## Thai Adaptations

- Caption/ประโยคภาษาไทย **ไม่ลงท้ายมหัพภาค** (ธรรมเนียมไทย; กฎ period ของ Google เป็น English-specific)
- คำบอกทิศทางใช้ได้บ้างในคู่มือภายในองค์กร ถ้ามีรูปอ้างอิง แต่ควรลด ใช้ชื่อปุ่มนำ
- คำกริยามาตรฐาน: **กด** (ปุ่ม) / **เลือก** (รายการ) / **กรอก, พิมพ์** (ข้อความ) / **เปิด** / **ดาวน์โหลด**

## Example

### Procedure Format

```markdown
## สร้างรายงาน

เพื่อสร้างรายงาน ทำตามขั้นตอนต่อไปนี้:

1. ที่หน้า **แดชบอร์ด** เลือกแท็บ **รายงาน**
2. กด **สร้างรายงานใหม่**
3. ในช่อง **ชื่อรายงาน** กรอกชื่อที่ต้องการ
4. เลือก **ประเภทรายงาน** จากเมนูแบบเลื่อนลง
5. กด **บันทึก** ระบบกลับไปหน้ารายการรายงาน

Optional: เพื่อตั้งค่าเพิ่มเติม เลือกแท็บ **ตั้งค่า**
```

## Common Mistakes

- เขียนแบบบรรยาย UI แทน task-focused
- ใช้คำกริยาอ้อมค้อมแทนคำสั่งตรง
- ไม่มี Quick Start ตอนต้น
- Screenshots ไม่มี annotations
- ใช้คำบอกทิศทาง (บน/ล่าง/ขวา) แทนชื่อปุ่ม
- ไม่ทดสอบกับผู้ใช้จริง
